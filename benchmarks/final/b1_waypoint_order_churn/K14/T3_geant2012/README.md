# B1 waypoint / IDS-bypass — T3 Geant2012, K14

This directory contains the **B1 waypoint-order** benchmark instance on the
**T3 Geant2012** topology with background-update churn level **K = 14**.

## A. Overview

The B1 waypoint-order family tests whether monitored traffic that is steered through a
designated waypoint (an inspection point) can be made to bypass that waypoint so that it
reaches its destination **uninspected**. Concretely, the benchmark checks the forwarding
property that traffic from the source must traverse the waypoint before the destination's
forbidden uninspected port can be reached.

- **Geant2012 in this configuration** is the concrete graph embedding for the race pattern:
  a 40-node / 61-edge research-network topology (diameter 8, cycle rank 22, connected, from
  the Internet Topology Zoo; full provenance in *Topology provenance* below). The embedding
  places a source node (`n028`), a waypoint node (`n023`) and a destination node (`n004`)
  into the switch model as `SW028`, `SW023` and `SW004`.
- **Faulty vs control comparison.** The two models are byte-for-byte identical except for a
  single semantic difference at the waypoint's initial flow table (see section D). The faulty
  model is expected to expose **harmful races** (the monitored traffic can reach the
  destination uninspected); the control model is expected to expose **zero** harmful races.
  The pair exists to show that the harness attributes the race to the waypoint-order
  condition rather than to the topology, the property, or the churn itself.

### `BSw:17` composition and semantics (verified)

`BSw` counts the alternatives of the big-switch expression that the RaceLoom model builder
emits for the network's switches. It is generated by `DNKMaudeModel.__buildBigSwMainExpr`
in the RaceLoom implementation, which is distributed separately from RaceLoom-Bench and is
not tracked in this repository (see *Implementation provenance for `BSw`* below). The
generated expression starts from one base default-forwarding alternative and appends one
alternative per `DirectUpdate` and one per `RequestedUpdate` across all switches.
`InitialFlowTable` entries are **not** counted by `BSw`; in particular, the destination
switch's initial forwarding table contributes nothing, and the faulty/control difference at
the waypoint `InitialFlowTable` (section D) therefore leaves `BSw` unchanged.

The committed K14 models (`bad/` and `control/` are identical in this respect) contain
exactly 16 `DirectUpdate`s and zero `RequestedUpdate`s, decomposed as follows:

| Contribution | Count |
|---|---:|
| Base default-forwarding alternative | 1 |
| Background `DirectUpdate`s — K = 14, one per background switch (`SW001`–`SW003`, `SW005`–`SW015`) | 14 |
| Ingress `DirectUpdate` (`SW028`) | 1 |
| Waypoint `DirectUpdate` (`SW023`) | 1 |
| Destination `DirectUpdate`s (`SW004` has none) | 0 |
| `RequestedUpdate`s | 0 |
| **`BSw` total** | **17** |

so `BSw = 1 + 14 + 1 + 1 + 0 + 0 = 17`, matching the historical signature `BSw:17` in both
logs. An earlier audit note described the model as containing "16 background-update switch
channels"; that was a miscount — 16 is the total number of `DirectUpdate`s (14 background +
ingress + waypoint), not the number of background channels.

**Implementation provenance for `BSw`.** The semantics above were verified against the
RaceLoom implementation source, which is distributed separately from RaceLoom-Bench (it is
not part of this repository, so no repository-relative source link is given). Reference:
Zenodo record `16884345`; archive size 794,997,198 bytes, MD5
`21ba15ae55de83d833a80c27b677e80e`, SHA-256
`bc533c637a0fa55e51f6c84c07137bdd44ddbd303c9a2443ab6301710ec58d45`; source file
`src/model/dnk_maude_model.py`, class `DNKMaudeModel`, function `__buildBigSwMainExpr`
(lines 177–209; the `BSw` branch count is recorded at line 208).

## D. Faulty / control semantics

The faulty and control models differ in exactly **one** semantic location, the waypoint
switch `SW023.InitialFlowTable`:

| Model | `SW023.InitialFlowTable` | Meaning |
|---|---|---|
| `bad/model.json` (faulty) | `(port = 8502) . (port <- 8510)` | Initially forwards monitored traffic **uninspected**. |
| `control/model.json` (control) | `(port = 8502) . (port <- 8503)` | Safe from the start. |

In **both** models the waypoint's post-update policy is the safe rewrite
`(port = 8502) . (port <- 8503)` (the `upWaypoint` update under `SW023.DirectUpdates`). The
fault therefore lives only in the *initial* state: under background churn the ordering
between the faulty initial table and the corrective update can let monitored traffic reach
the destination's forbidden uninspected port before the waypoint is corrected. The control
model removes that window by starting safe.

The only other difference between the two model files is the resulting file hash; the
relevant initial-flow-table line is the sole semantic delta.

## E. Property

Both models are checked against the same forwarding property:

```text
(port=2) . @Network . (port=8513)
```

with `AllowsPackets=false` (i.e. packets matching this path are **forbidden**). It is
instantiated in `properties.json` under three entry-point names (`CT->SW`, `CT->SW<-CT`,
`CT->CT->SW`), all with the same expression and `AllowsPackets=false`. Positive
(`harmful races`) counts in the faulty model therefore represent reachable violations of the
forbidden uninspected path.

`bad/properties.json` and `control/properties.json` are byte-identical. Shared SHA-256:

```text
3fd72e9a9f97b09213799cf636b35f4b914af54cdd01f0c1bd8bd01fd962df95
```

This configuration was **independently re-executed at this commit** through the canonical
pipeline (`scripts/run_final_matrix.sh` → `scripts/run_one_pair.sh` →
`scripts/run_raceloom_progress.sh`) on the project's Linux amd64 validation server
(Docker) on 2026-11-04,
using the RaceLoom runtime image `sha256:fe13627b75f8e7c8c3d2299a1090f2eeac255785b4a569ad5b84766180e24087`
at repository HEAD `ac837210b919c5b91ae3b4dd445935b5e937a083`. The independent checker
`scripts/check_final_matrix.py` classified the configuration **`SCIENTIFIC_MATCH`**: the
freshly generated faulty side produced 82,688 traces with 44 harmful races and the control
side produced 82,688 traces with 0 harmful races, matching the historical expectations
(`docs/final_4x4_matrix.tsv` and the 2026-06-05 sanitized logs), including the branch
signature. The execution-time provenance record ties the executed inputs cryptographically
to the committed files (SHA-256: `bad/model.json` `603f5c0f…c1c400`,
`control/model.json` `ccb44e06…2e26e9f`, shared properties `3fd72e9a…62df95`). The fresh
console logs, `final_stats.csv` files, harmful-trace artifacts, and provenance records are
preserved in the release evidence archive.

Still accurate limitations (unchanged by the reproduction):

- **The historical logs contain no model hash**, so the 2026-06-05 logs alone cannot be tied
  cryptographically to the committed `bad/model.json` / `control/model.json`. The historical
  match is by encoding signature (branch signature above) and by the documented
  faulty/control `InitialFlowTable` difference. The 2026-11-04 reproduction closes this gap
  for the current commit via its provenance record, not retroactively for the historical logs.
- The historical logs reference model/property paths under the older directory name
  `benchmarks_comprehensive_topologies/b1_waypoint_order_churn/...`; the committed tree is
  `benchmarks/final/b1_waypoint_order_churn/...`. The rename is not recorded inside the logs.
- The `RaceLoom finished with exit code: 0` lines in the historical logs were appended by a
  historical progress wrapper; the appended line does not affect the reported statistics.
- The `metadata.json` status field remains `generated_unvalidated`: the metadata file itself
  was not rewritten to assert historical validation blocks. The independent reproduction
  evidence lives in the release evidence archive and is summarized in `docs/RESULTS.md`.

## I. Running this configuration

This configuration is executed through the canonical pipeline; there is no per-configuration
`run.sh` in this directory (the historical `run.sh` helpers of some sibling configurations
predate the canonical pipeline and are not required). Equivalent single-configuration
execution:

```bash
export RACELOOM_IMAGE=raceloom:latest
export RACELOOM_MATRIX_OUTPUT_ROOT=/path/to/evidence-root
export RACELOOM_MATRIX_ONLY=B1_K14_T3_geant2012
bash scripts/run_final_matrix.sh
```

or directly through the pair runner:

```bash
export RACELOOM_IMAGE=raceloom:latest
bash scripts/run_one_pair.sh benchmarks/final/b1_waypoint_order_churn/K14/T3_geant2012 4 /path/to/console-dir
```

See `docs/REPRODUCTION.md` for the complete procedure and `docs/VALIDATION.md` for the
independent checker.
